# Iteration 5: bounded head polling before cooperative yield

The guard model now permits a mismatching head comparison to return directly to the next atomic head Load or to take the existing cooperative-yield path. A matching comparison still has exactly one successor: entering the guarded body. Ticket allocation, counter width, full-word Try CAS, release CAS, normalization, and ownership checks are unchanged. The product candidate uses at most 64 mismatching head loads before yielding; the model deliberately does not encode that budget.

All 44 guard configurations pass exhaustively: 263,419 states and 1,069,253 edges. The state count is unchanged from iteration 3; the optional polling path adds 121,913 edges. Thirty bounded configurations cover every blocking/Try assignment for one through four actors. Fourteen continuous-traffic configurations cover a blocking victim with every repeating blocking/Try assignment for two through four actors. The extra packed-Try wrap graph passes with 125 states and 247 edges. The separate-counter Try negative retains its 40-transition witness ending in two owners (93 states and 179 edges).

The additional edge runs from a mismatching `guardDecide` state to `guardPoll`. It changes only that caller's control phase and retains the next shared atomic read. The existing forced-yield model can simulate this edge by inserting its local `guardYield` step before the same read. That extra local step changes no counter, ticket, snapshot, or ownership state and introduces no new actor's enablement. Since scheduling between reads was already unconstrained, this simulation preserves the observable ticket execution and strong actor fairness. Making the optional edge explicit provides a fresh exhaustive check of the candidate's actual polling order.

The new graph conservatively allows arbitrarily many consecutive mismatch polls, including infinitely many. This makes the safety and conditional liveness gate stronger than one for a fixed 64-poll budget. Each preceding head holder has a finite guarded body and finitely many release-CAS interference opportunities under the outstanding-claim bound. Strong actor fairness therefore advances it. Once the victim ticket is the head, that head cannot advance past the victim: its next atomic Load returns a match and its next comparison enters the body. Busy polling cannot overtake another ticket, claim a future ticket, or continually postpone a matching head.

The graph does not verify the native cooperative-yield budget. A separate deterministic product test must verify a yield occurs after 64 mismatching loads, the count does not reset on each mismatch, and a matching head enters immediately. A budget-reset mutant may violate that scheduling requirement while remaining safe in this conservative graph, so it must be killed by the native budget test rather than claimed as a model counterexample. No performance result follows from this gate.

The new mismatch-choice test failed before the optional edge was added; the matching-head test already passed. Both pass after the change. A mutation that prevents matching-head entry fails the entry assertion. A mutation that loops through the cached mismatch without the next atomic head Load produces a fair starvation cycle with two actors: the victim repeatedly branches on its stale mismatch while the other actor also makes progress. The latter control demonstrates why every continued probe must read the shared head anew. Exact changed text, commands and outcomes are in `guard-v5-poll-mutations.json`.

This historical guard change left the Mutex, RWMutex and fairness engine unchanged from the release-shortcut candidate. Their finite public graphs therefore remain the iteration-4 results: Mutex 20 configurations / 11,911,188 states / 42,532,319 edges; RWMutex 20 / 3,057,977 / 12,207,118. Their guard composition is strengthened by this explicit polling analysis. The ticket rank, fewer-than-2^32 outstanding-claims capacity, finite guarded-body, and release-CAS finite-interference arguments remain those in `model-v3-review.md`. This iteration does not change the release shortcut or introduce pre-registration spinning.
